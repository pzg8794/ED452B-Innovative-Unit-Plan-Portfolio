# Unit Reflection and Critical Evaluation

## What the Unit Confirmed

The Minecraft lessons confirmed that engagement is not the same as access. Students were interested in the digital environment, but interest alone did not guarantee that they understood the task, read the NPC directions, entered the correct world, or knew how to debug the Agent.

This confirmed the theoretical framework behind the unit: inclusive instruction must be designed before students fail. Supports like projected click paths, NPC read-alouds, Driver/Navigator roles, and debugging protocols are not extras. They are part of making the content measurable and teachable.

## What Went Well

- Minecraft made algorithms visible because students could immediately see whether the Agent moved as expected.
- Students were motivated by the environment and wanted to solve the challenges.
- Teacher conferencing naturally surfaced student reasoning.
- Specific hints helped students continue without having the answer given away.
- Students with prior Minecraft knowledge could be positioned as resources.

## Problems and Dilemmas

The biggest dilemma was that Minecraft introduced several access barriers at once:

- login and loading time;
- finding the correct world;
- interpreting NPC text;
- understanding the goal;
- using keyboard and mouse controls;
- translating a path into code;
- explaining the code afterward.

This made assessment tricky. A student could appear unsuccessful even when the barrier was not computational thinking. Conversely, a student could complete a task through prior Minecraft knowledge but still need support explaining the algorithm.

## Future Teaching Changes

In the next enactment, I would:

1. start every lesson with a projected click path;
2. use a one-minute task-goal restatement before coding;
3. require Stop-Read-Predict before the first Run;
4. collect screenshots of code and planning sheets as evidence;
5. conference with target students during each lesson;
6. make role-switching explicit so both partners explain the code;
7. use a hints-before-rescue protocol to avoid taking over student thinking.

## Critical Reflection

The unit changed my understanding of inclusive computer science instruction. It helped me see that the question is not only whether students can code. The deeper question is whether the classroom environment allows their coding knowledge to become visible.

A strong inclusive CS unit must ask:

- What is this task really measuring?
- Is the barrier conceptual, linguistic, executive-functioning, social, or technical?
- What support helped the student participate more independently?
- How can that support become part of the next lesson design?

That is the central professional learning from this unit.
