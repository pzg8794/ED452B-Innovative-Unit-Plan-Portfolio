# Assessment Plan

## Assessment Principle

The unit does not assess students only by asking whether they finished the Minecraft challenge. A completion-only score would hide too much. Students may struggle because of sign-in, navigation, NPC reading, unclear goals, partner-role confusion, or regulation demands rather than weak computational thinking.

The assessment plan therefore separates five evidence areas:

1. **Access** - Can the student enter the coding environment with the available supports?
2. **Goal understanding** - Can the student restate what the Agent is supposed to do?
3. **Algorithmic planning** - Can the student break the path into ordered steps?
4. **Debugging** - Can the student notice a mismatch and revise one part of the code?
5. **Explanation** - Can the student explain one code choice, bug, fix, or efficiency decision?

## Evidence Sources

| Evidence source | Purpose |
|---|---|
| Startup / world-entry checklist | Separates interface access from coding knowledge. |
| Plan Before You Code worksheet | Shows decomposition and sequencing before the student runs code. |
| Teacher conference notes | Documents prediction, debugging, and student explanation. |
| Code screenshot or observed code run | Shows whether the Agent followed the intended algorithm. |
| Debug log | Shows what students expected, what happened, and what they changed. |
| Exit ticket | Captures reflection and vocabulary use. |
| Oral explanation | Allows CLD learners and students with writing needs to show understanding without being limited to written output. |

## Expanded Unit Rubric

| Criterion | Meets | Approaching | Needs support |
|---|---|---|---|
| Followed directions | Restates the task goal and follows room directions. | Follows some directions but needs clarification. | Begins coding without understanding the goal. |
| Reached correct goal path | Agent reaches intended target or student revises effectively toward it. | Agent reaches part of the path or succeeds after substantial prompting. | Code does not yet connect to the goal path. |
| Used efficient code | Uses movement, turns, loops, or shortcuts effectively. | Code works but includes unnecessary blocks or inefficient pathing. | Code is mostly random or not yet planned. |
| Used access supports productively | Uses checklist, role card, NPC card, or planning sheet with independence. | Uses support after prompting. | Does not yet use available support. |
| Explanation / reflection | Explains one code choice, bug, fix, or efficiency decision. | Gives a partial explanation with frame or oral support. | Cannot yet explain the code choice, even with support. |

## Feedback Approach

Feedback is targeted and tied to the evidence source. Examples:

- "You understood the goal after rereading the NPC card. Next time, use Stop-Read-Predict before pressing Run."
- "Your Agent stopped one block short. Count the path again and change one block only."
- "Your loop made the code easier to read. Explain what repeated action belongs inside the loop."
- "You used the Navigator role well because you asked a question instead of grabbing the keyboard."

## Why This Meets the Rubric

The ED452B rubric asks for multiple formative and summative assessment methods that align with goals, document learning progressions, and help students receive specific feedback. This assessment plan does that by treating planning, testing, revision, explanation, and productive use of supports as evidence of learning.
